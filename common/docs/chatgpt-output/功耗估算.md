可以，而且要把“充电器是否接入”“电池到底在充还是放”“整机正在消耗多少功率”分成三个独立量。**不要用一个 BATTERY 电流正负号同时表达这三件事。**

Android 官方 `BatteryManager` 和 Linux 标准 `power_supply` ABI 的约定其实都是：**电池充电为正，放电为负，单位通常为 µA**。但 OEM 的 HAL、fuel gauge 驱动、厂商私有 sysfs 节点确实可能实现错误、反号或单位不同，所以做跨华为/小米/荣耀/OPPO/vivo/三星设备的工具时，应该做运行时校准，而不是维护“品牌正负号表”。([Android Developers](https://developer.android.com/reference/android/os/BatteryManager?authuser=0&utm_source=chatgpt.com))

## 1. 先定义你自己的统一物理模型

建议程序内部永远使用：

```text
I_bat > 0   电流流入电池，电池净充电
I_bat < 0   电流流出电池，电池净放电

P_bat = V_bat × I_bat

P_bat > 0   电池储能功率
P_bat < 0   电池向手机供电功率
```

例如：

```text
Vbat = 4.00 V
Ibat = +1.2 A
=> 电池正在以约 4.8 W 净充电

Vbat = 4.00 V
Ibat = -0.8 A
=> 电池正在提供约 3.2 W
```

UI 上不要直接显示原始值，而显示：

```text
Battery net current: +1200 mA
Battery charge power: 4.8 W

或者

Battery net current: -800 mA
Battery discharge power: 3.2 W
```

这样以后不管厂商怎么反号，你只在采集层转换一次。

## 2. “插着充电器但仍然放电”完全可能

这是你问题中最容易混淆的一点。

实际供电拓扑大致是：

```text
          ┌──── 手机 CPU/GPU/屏幕/射频...
充电器 ───┤
          └──── 电池
```

充电器接入并不意味着电池一定正在充电。

例如：

```text
充电器实际提供：5 W
手机此时消耗：  8 W
不足的：        3 W
```

那么：

```text
ExternalPowerPresent = true
BatteryStatus         = Discharging
I_bat                 < 0
```

也就是说：

> 手机“正在充电/插着充电器”的 UI 状态，和电池的瞬时净能量流向不是同一个概念。

Linux 的 fuel-gauge 驱动甚至明确处理这种情况：外部电源存在，但如果它提供的功率不够，电池仍可以处于 `DISCHARGING`。([GitHub](https://github.com/torvalds/linux/blob/master/drivers/power/supply/max17042_battery.c?utm_source=chatgpt.com))

因此你程序里至少应该保存：

```text
ExternalPowerPresent
BatteryNetCurrent
BatteryNetPower
BatteryStatus
```

而不是简单的一个：

```text
IsCharging
```

# 3. 最可靠的电池电流获取优先级

如果你走 ADB，我建议按下面优先级。

### 第一层：Android framework / health 数据

先试：

```bash
adb shell dumpsys batteryproperties
```

不同 Android/OEM 输出不同，可能出现：

```text
status: 2
level: 53
voltage: 4012
current now: -734215
charge counter: 2274000
```

以及：

```bash
adb shell dumpsys battery
```

主要拿：

```text
AC powered
USB powered
Wireless powered
status
level
voltage
temperature
```

但注意：`dumpsys batteryproperties` 虽然接近 Android BatteryManager 的来源，OEM HAL 仍可能给反号。

### 第二层：枚举 Linux power_supply

不要写死：

```text
/sys/class/power_supply/battery
```

应该枚举：

```bash
adb shell 'for d in /sys/class/power_supply/*; do echo ===$d===; cat $d/type 2>/dev/null; done'
```

因为实际可能有：

```text
battery
Battery
bms
usb
USB
ac
charger
main
pc_port
wireless
dc
```

然后针对每个节点探测：

```text
type
status
online

current_now
current_avg
voltage_now
voltage_avg

charge_counter
charge_now
energy_now
power_now

current_max
input_current_limit
input_voltage_limit
input_power_limit
```

Linux 标准规定 `current_now/current_avg`、`voltage_now` 等标准属性使用 µA/µV，电池 current 的标准方向是**充电正、放电负**。([Linux 内核归档](https://www.kernel.org/doc/html/latest/power/power_supply_class.html?utm_source=chatgpt.com))

但是：

> 厂商自己增加的非标准节点不能相信这个约定。

# 4. 最强方案：用 Charge Counter 自动校准正负号，甚至校准单位

这非常适合你的多设备工具。

如果设备存在：

```text
charge_counter
```

或者 Android：

```text
BATTERY_PROPERTY_CHARGE_COUNTER
```

它代表电池电量，通常单位 µAh。Linux 文档也明确指出 charge counter 特别适合做**相对时间测量**。([Linux 内核归档](https://www.kernel.org/doc/html/latest/power/power_supply_class.html?utm_source=chatgpt.com))

假设在一段时间内：

```text
Q0 = 2,000,000 µAh
Q1 = 2,010,000 µAh
dt = 60 s
```

那么实际平均电池电流：

```text
ΔQ = Q1 - Q0

I_cc = ΔQ / Δt(hours)

     = ΔQ × 3600 / Δt_seconds
```

上例：

```text
I_cc
= 10000 × 3600 / 60
= +600000 µA
= +600 mA
```

所以无论厂商 `current_now` 给你：

```text
+610000
```

还是：

```text
-610000
```

你都能知道真实方向。

更进一步，假设厂商私有节点输出：

```text
current_now = -610
```

而 charge-counter 算出来是：

```text
+600000 µA
```

那么：

```text
k ≈ -1000
```

你同时发现了：

```text
方向反了
单位是 mA 而不是 µA
```

## 我建议你的自动校准算法

采集 60~180 秒：

```text
Q_start
Q_end

raw_current[0...N]
```

算：

```text
I_cc_uA =
    (Q_end - Q_start) * 3600 / elapsed_seconds

I_raw_avg =
    trimmed_mean(raw_current)

K =
    I_cc_uA / I_raw_avg
```

如果 K 稳定接近：

```text
+1
-1
+1000
-1000
+0.001
-0.001
```

就可以得到：

```text
单位倍率
+
正负方向
```

最终统一：

```text
I_bat_uA = raw × calibrated_scale
```

这比：

```text
if Huawei => negate
if Xiaomi => don't negate
```

稳健得多。

# 5. 没有 charge_counter 怎么办

降级策略：

### A. 已知是标准 BatteryManager

按 Android API 约定：

```text
+ = charging
- = discharging
```

Android 官方明确如此定义。([developer.android.com](https://developer.android.com/reference/android/os/BatteryManager?authuser=0&utm_source=chatgpt.com))

### B. 标准 `/sys/class/power_supply/.../current_now`

原则上同样：

```text
+ = charging
- = discharging
```

Linux ABI 同样明确规定。([GitHub](https://github.com/torvalds/linux/blob/master/Documentation/ABI/testing/sysfs-class-power?utm_source=chatgpt.com))

### C. OEM 私有节点

做一次运行态实验：

```text
拔掉 USB
等待 10~30 秒
```

此时只要手机不是在特殊外部供电状态，电池一定在向外供电。

因此采样均值：

```text
raw = +800000
```

就知道 OEM 定义为：

```text
+ = discharge
```

然后程序保存：

```text
polarity = -1
```

最好把校准结果缓存到：

```text
manufacturer
model
device
product
hardware
soc
build fingerprint
sensor path
```

组合 key 上。

但是系统 OTA 后应该重新验证。

# 6. 不要直接使用一个瞬时 current_now

手机电流变化极大，例如：

```text
200 mA
350 mA
2100 mA
-50 mA
900 mA
...
```

CPU boost、屏幕刷新、基带发射都会造成瞬态。

建议采样周期：

```text
0.5~1 秒
```

ADB 本身没必要追求几十 Hz。

UI 同时维护：

```text
Instant        当前值
5s average     快速变化
30s average    推荐显示值
60s average    功耗估算
```

例如采用：

```text
median filter
+
EMA
```

或者简单一点：

```text
最近 30 个样本去掉最高 10%
和最低 10% 后取平均
```

对 ADB 工具已经足够稳定。

# 7. 怎样计算“手机当前功耗”

这里要分两种情况。

## 情况 A：没有接充电器

这是最好测的。

如果：

```text
Ibat = -850 mA
Vbat = 3.95 V
```

则：

```text
P_phone ≈ 3.95 × 0.850
        ≈ 3.36 W
```

所以：

```text
P_phone ≈ -P_bat
```

这是软件方式里非常有价值的**整机实际功耗测量值**。

它比 CPU 使用率之类的模型靠谱得多，因为这是 battery fuel gauge 实际看到的电流。

# 8. 插着充电器后，仅靠 BATTERY current 无法知道手机总功耗

例如：

```text
Battery:
4.0 V
+1000 mA
```

你只能知道：

```text
电池得到约 4 W
```

但不知道充电器提供的是：

```text
5 W
```

还是：

```text
10 W
```

如果：

```text
Pin = 10 W
Pbat = +4 W
```

那么：

```text
手机其余部分消耗约 6 W
```

但如果：

```text
Pin = 5 W
Pbat = +4 W
```

整机其余部分只有约：

```text
1 W
```

所以仅有 `battery/current_now` 无法反推。

# 9. 如果能得到 USB/VBUS 实际电压、电流，就能解决

定义：

```text
P_port = VBUS × IBUS
```

注意一定要是**实际测量值**。

不能拿：

```text
current_max
input_current_limit
voltage_max
```

直接算。

这些通常表示：

> 上限/协商值/配置值

而不是现在真正消耗的电流。

如果对应 USB power_supply 节点真的提供：

```text
voltage_now
current_now
```

那么 Linux ABI 对 USB `current_now` 的定义就是实际 IBUS 电流。([GitHub](https://github.com/torvalds/linux/blob/master/Documentation/ABI/testing/sysfs-class-power?utm_source=chatgpt.com))

于是统一公式非常漂亮：

```text
P_device ≈ P_port - P_bat
```

其中仍规定：

```text
P_bat > 0  电池吸收功率
P_bat < 0  电池输出功率
```

举两个例子。

### 手机正在充电

```text
USB输入       10 W
电池净充电     6 W

手机消耗 ≈ 10 - 6
         ≈ 4 W
```

### 插着 USB，但电池仍在放电

```text
USB输入        3 W
电池           -2 W
```

于是：

```text
手机消耗 ≈ 3 - (-2)
         ≈ 5 W
```

这恰好就是你描述的：

> “在充电，但充电速率不如放电速率。”

更准确的说法应该是：

> **外部供电存在，但外部输入功率不足以覆盖设备负载，因此电池同时补充供电。**

------

# 10. 如果 USB 节点没有实际 IBUS，软件无法精确知道充电状态下的整机功耗

这必须明确。

如果你只能拿到：

```text
VBUS = 9V
input_current_limit = 2A
```

你只能知道：

```text
理论输入上限 ≈ 18 W
```

绝对不能显示：

```text
当前功耗 = 18 W
```

实际上可能只有：

```text
3.5 W
7 W
12 W
```

这种情况下最可靠的 ground truth 仍然是：

```text
USB-C 功率计
+
手机 BATTERY current
```

然后：

```text
P_device = P_USB_meter - P_battery
```

这还能用于反过来验证你各个 OEM 的 sysfs 采集器。

# 11. 进程级功耗：不要承诺“精确”，只能做 attribution

这是另一套问题。

物理传感器可以告诉你：

```text
整机正在耗 4.7 W
```

但无法直接告诉你：

```text
微信 0.7 W
抖音 2.1 W
SystemUI 0.2 W
```

因为：

```text
CPU
GPU
Display
DRAM
Wi-Fi
5G modem
GPS
Bluetooth
ISP
DSP
```

大量资源是共享的。

Android 通用方案是：

```bash
adb shell dumpsys batterystats
```

它可以提供：

> 每个 UID 和系统组件的大致耗电量。

官方也明确称其为 approximate power use。([Android Developers](https://developer.android.com/tools/dumpsys?hl=zh-cn&utm_source=chatgpt.com))

它背后通常结合：

```text
UID CPU 时间
CPU frequency/state
wakelock
network
Wi-Fi
radio
GPS
Bluetooth
screen 等
```

和 OEM：

```text
power_profile.xml
```

建立模型。

AOSP 明确说明：`BatteryStats` 并不是直接给每个进程装一个电流表，而是统计各组件状态持续时间，再用设备的 power profile 估算 mAh。([Android Open Source Project](https://source.android.com/docs/core/power?hl=zh-CN&utm_source=chatgpt.com))

因此跨厂商：

```text
同一 App：
华为显示 35 mAh
小米显示 48 mAh
```

不应该拿来作绝对横向比较。

但同一台机器上的：

```text
App A vs App B

或者

版本 1.0 vs 1.1
```

非常有参考价值。

问题在于：

所以应该当：

```text
高级可选 capability
```

而不是基础依赖。

# 14. 我建议你最终实现成四级数据质量

如果要集成进你现在的 Android/ADB 管理工具，我建议抽象成：

```text
Level A — Measured
Battery current + battery voltage
=> 实际电池功率

Level B — Measured Input
Battery current + USB actual IBUS/VBUS
=> 实际整机功耗

Level C — Android Attribution
BatteryStats / PowerStats
=> UID/package 估算功耗

Level D — Model Attribution
CPU time/freq + process stats + power_profile
=> 自己估算的 process 功耗
```

并且 UI 明确区分：

```text
Measured
Estimated
Unavailable
```

绝对不要为了 UI 好看，在缺传感器的时候猜一个“当前 3.72 W”。

------

## 我会特别建议采用这样的内部数据结构

```csharp
PowerSnapshot
{
    bool ExternalPowerPresent;

    double? BatteryVoltageV;

    // 统一约定：
    // >0 charging
    // <0 discharging
    double? BatteryCurrentA;

    double? BatteryPowerW;

    double? InputVoltageV;
    double? InputCurrentA;
    double? InputPowerW;

    double? DevicePowerW;

    CurrentDirectionSource DirectionSource;
    PowerMeasurementQuality Quality;

    string BatteryCurrentSource;
    double? CalibrationScale;
}
```

其中：

```text
BatteryPowerW =
    BatteryVoltageV * BatteryCurrentA

DevicePowerW =
    InputPowerW - BatteryPowerW
```

然后 UI 可以非常直观：

```text
外部供电        USB-PD
输入功率        8.72 W       [Measured]

电池电流        +0.93 A
电池功率        +3.81 W      [Measured]
状态            净充电

设备功耗        4.91 W       [Measured]
```

或者：

```text
外部供电        USB
输入功率        unavailable

电池电流        -0.71 A
电池功率        -2.85 W      [Measured]
状态            外部供电 + 电池补电

设备功耗        unavailable
```

这比显示一个模棱两可的“充电速度”要准确很多。

**最关键的三条规则是：**

1. `BATTERY current` 永远解释为**电池净电流**，不是充电器电流。
2. OEM 正负号用 `charge_counter` 的时间导数自动校准，不维护品牌表。
3. 充电状态下想算整机真实功耗，必须再有 **VBUS/IBUS 实际输入功率**；只有 battery current 在物理上信息不足。

如果按这个模型实现，华为 Android 10/12、小米较新的 Android，以及未来其他 OEM 都可以共用同一套核心算法，差异只留在最底层的 `PowerSensorProvider`。
